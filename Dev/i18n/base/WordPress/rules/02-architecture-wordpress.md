# WordPress Architecture

> Scope: WordPress 7.1 line (PHP 7.4 minimum, 8.3+ recommended), plugins and block themes. Out of scope: Bedrock, hosting and multi-environment deployment, generic PHP design (see the `php` stack), frontend frameworks outside the block editor. WooCommerce specifics are in the optional `woocommerce` skill, not here.

## Principle

Extend core through its public APIs (hooks, blocks, REST, Settings API); keep the plugin a thin wiring layer over plain, testable PHP classes. Never edit core or other plugins; if behavior must change, use or provide a filter.

## Plugin Bootstrap

The main file carries the header and bootstraps; nothing else. See `templates/plugin-bootstrap.md` for the full skeleton.

```php
<?php
/**
 * Plugin Name:       Acme Reports
 * Version:           1.0.0
 * Requires at least: 6.6
 * Requires PHP:      7.4
 * Requires Plugins:  some-dependency
 * Text Domain:       acme-reports
 * Domain Path:       /languages
 * License:           GPL-2.0-or-later
 */

defined( 'ABSPATH' ) || exit;

require_once __DIR__ . '/vendor/autoload.php';

add_action( 'plugins_loaded', array( new Acme\Reports\Plugin( __FILE__ ), 'boot' ) );
```

- `Requires at least` and `Requires PHP` reflect what CI tests, not what is wished; `Requires Plugins` lists hard dependencies by WordPress.org slug (WordPress blocks activation if they are missing)
- One PSR-4 namespace and one function/option/hook prefix per plugin; the text domain equals the plugin slug
- Activation, deactivation and uninstall are separate, idempotent entry points (`register_activation_hook`, `register_deactivation_hook`, `uninstall.php`)

## Suggested Layout

```
my-plugin/
├── my-plugin.php
├── uninstall.php
├── readme.txt
├── src/
│   ├── Plugin.php                # boot(): registers features
│   ├── Admin/                    # Settings pages, admin notices
│   ├── Rest/                     # WP_REST_Controller subclasses
│   ├── Cli/                      # WP-CLI commands
│   ├── Domain/                   # Plain PHP, no WordPress calls
│   └── Blocks/<block>/           # block.json, render.php, edit.js, view.js
├── build/                        # Generated by wp-scripts
├── languages/
└── tests/
```

Use Vertical Slices per feature when the plugin grows; do not add layers a 500-line plugin does not need (YAGNI).

## Hooks

- Register hooks in one `register()` / `boot()` method per feature, on the earliest hook that has what you need: `plugins_loaded` (wiring), `init` (post types, taxonomies, blocks, shortcodes), `admin_init`, `rest_api_init`, `wp_enqueue_scripts`, `admin_enqueue_scripts`
- Callbacks are public methods or named functions so integrators can `remove_action()` them; document priority when order matters
- Provide your own prefixed `apply_filters()` / `do_action()` points for behavior integrators may change; document each with a docblock (`@since`, `@param`)
- Keep callbacks thin: map hook arguments to a domain method

```php
add_action( 'save_post_acme_report', array( $this->handler, 'on_save' ), 10, 2 );
// Later, from another plugin:
remove_action( 'save_post_acme_report', array( $handler, 'on_save' ), 10 );
```

## Data

| Need | Use |
|------|-----|
| Configuration | `register_setting()` + Settings API; one array option per feature; `autoload` false when not read on every request |
| Content | Custom post types and taxonomies registered on `init`, `show_in_rest` when the editor needs them |
| Per-object data | Registered meta (`register_post_meta()` with `show_in_rest`, `sanitize_callback`, `auth_callback`) |
| Large or relational data | Custom table created by `dbDelta()`, versioned with a `db_version` option and upgrade routine |
| Expensive results | Transients, or the object cache (`wp_cache_get/set` with a group) with explicit expiry and invalidation |

Always use `$wpdb->prefix` for table names and `$wpdb->prepare()` for SQL.

## Queries and Performance

- Never `posts_per_page => -1` on user-reachable code; paginate or cap
- `no_found_rows => true` when the total is unused; `fields => 'ids'` when only ids are needed; disable meta/term cache priming when unused
- Avoid `meta_query` and `orderby => meta_value` on large sites (the `wp_postmeta` table is not indexed for value lookups); prefer taxonomies or a custom table
- Do not query inside loops; prime caches or batch
- Modify the main query with `pre_get_posts`, never `query_posts()`; restore with `wp_reset_postdata()` after secondary loops
- Keep early hooks cheap; defer to the relevant context (`is_admin()`, `wp_doing_ajax()`, REST)
- Schedule background work with `wp_schedule_event()` guarded by `wp_next_scheduled()`; unschedule on deactivation; chunk long jobs

## Blocks

- One folder per block with a `block.json` (`apiVersion` 3, namespaced `name`, `textdomain`, `attributes`, `supports`). See `templates/block.md`
- Register all blocks at once from the build manifest (recommended since WordPress 6.8): `wp_register_block_types_from_metadata_collection( __DIR__ . '/build', __DIR__ . '/build/blocks-manifest.php' )` on `init`; `wp-scripts build --blocks-manifest` or `wp-scripts build-blocks-manifest` generates the manifest. For a single block, `register_block_type( __DIR__ . '/build/my-block' )` remains valid
- Dynamic blocks render in PHP (`render.php`, or `render_callback`): the `$attributes`, `$content` and `$block` variables are available, output is escaped late, and the wrapper uses `get_block_wrapper_attributes()`
- Static blocks save markup in JS; any change to saved markup needs a `deprecated` entry so existing content keeps validating
- Front-end interactivity uses the Interactivity API: `viewScriptModule` in `block.json`, `data-wp-interactive`, directives such as `data-wp-on--click` and `data-wp-bind--*`, a namespaced `store()` from `@wordpress/interactivity`, and server state via `wp_interactivity_state()`. Script modules need the `--experimental-modules` flag on `wp-scripts build`/`start` unless your scaffold already sets it
- Block bindings and patterns are preferred over custom shortcodes for new content structures

## Block Themes

- `style.css` (header), `theme.json` with `"version": 3`, `templates/*.html`, `parts/*.html`, `patterns/*.php` (with a pattern header: `Title`, `Slug`, `Categories`), `styles/` for variations
- Put design decisions (palette, typography, spacing, layout, per-block styles) in `theme.json`; use CSS only for what `theme.json` cannot express
- Declare `templateParts` and `customTemplates` in `theme.json`; keep PHP in `functions.php` minimal (enqueue, patterns, block style registration)
- Child themes inherit templates and `theme.json`; override sparingly

## REST API

- `register_rest_route()` on `rest_api_init`, vendor namespace and version (`acme/v1`), `permission_callback` on every route, `args` with `type`, `required`, `sanitize_callback`, `validate_callback` (or a JSON schema). See `templates/rest-endpoint.md`
- Prefer `WP_REST_Controller` conventions (`get_item_schema()`, `prepare_item_for_response()`); return `WP_REST_Response` or `WP_Error` with the right HTTP status
- Reuse domain services; the controller only maps request to call to response

## WP-CLI

```php
if ( defined( 'WP_CLI' ) && WP_CLI ) {
	WP_CLI::add_command( 'acme reports', Acme\Reports\Cli\Reports_Command::class );
}
```

- Commands reuse the same domain classes as hooks and REST; they never duplicate logic
- Document arguments with the PHPDoc synopsis (`## OPTIONS`, `## EXAMPLES`); use `WP_CLI::success()`, `warning()`, `error()` and `WP_CLI\Utils\make_progress_bar()` for batches

## Internationalization

- Literal strings and a literal text domain in every call: `__( 'Report', 'acme-reports' )`, `esc_html__()`, `_x()`, `_n()`; never concatenate or interpolate translatable strings, use `sprintf()` with placeholders and translator comments
- Since WordPress 4.6 translations are loaded from WordPress.org for hosted plugins; for bundled translations set `Domain Path` and call `load_plugin_textdomain()` only if needed
- JavaScript: `import { __ } from '@wordpress/i18n'` and `wp_set_script_translations( $handle, 'acme-reports', plugin_dir_path( __FILE__ ) . 'languages' )`; blocks registered from `block.json` get script translations when `textdomain` is set
- Generate the template with `wp i18n make-pot`

## Assets

- Register and enqueue with `wp_register_script()` / `wp_enqueue_script()`; read `build/*.asset.php` for `dependencies` and `version`
- Enqueue only where needed (block `style` / `viewScriptModule`, conditional `wp_enqueue_scripts`, `admin_enqueue_scripts` with the hook suffix)
- Use `wp_add_inline_script()` / `wp_add_inline_style()` instead of inline tags; load in the footer or with `strategy` => `defer` where possible

```php
$asset = include plugin_dir_path( __FILE__ ) . 'build/admin.asset.php';
wp_enqueue_script( 'acme-admin', plugins_url( 'build/admin.js', __FILE__ ), $asset['dependencies'], $asset['version'], array( 'in_footer' => true ) );
```

## Settings API

- `register_setting()` with `type`, `sanitize_callback`, `default`; `add_settings_section()` / `add_settings_field()`; render with `settings_fields()` and `do_settings_sections()`
- The admin menu entry declares a capability; the settings form relies on the Settings API's built-in nonce and the `options.php` handler, so no hand-rolled save code is needed

## Anti-Patterns

| Anti-pattern | Fix |
|--------------|-----|
| Logic and side effects at file scope | Bootstrap class on `plugins_loaded` / `init` |
| Generic global names (`save_data()`) | Namespace or unique prefix |
| `query_posts()`, `posts_per_page => -1` | `pre_get_posts`, pagination |
| Inline `<script>` / `<style>` in templates | `wp_enqueue_*` and `wp_add_inline_*` |
| Direct DB writes to core tables | Core APIs (`wp_insert_post`, `update_user_meta`) |
| Editing another plugin's files | Use or add a hook |
| Many scalar autoloaded options | One array option, `autoload` false |
